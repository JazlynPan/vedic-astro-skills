# Vedic 盲问全量扫描与锁定协议 v1.3

> 用途：在已有 `vedic-core` 或 `vedic-core-pro` 盘面审计基础上，回答“过去N年哪一年最……”或“猜一件我没告诉你的前事”等盲问。  
> 本协议不修改任何Vedic skill；只在用户明确要求盲问验证时，作为该次任务的附加执行要求。

## 必须怎样启动

本协议默认执行的是**UC隔离盲审**：`user_context.md`、聊天传记和已知事件可以存在，
但不得参与结论生成、候选选择、权重、停止点或置信度。核心目标是强制完整扫描，
杜绝照着UC解释和找到一个支持点就提前收敛。

只有用户明确要求证明“答案在分析前从未泄漏”时，才升级为
**防泄漏盲测**，并要求新的Codex任务和净化数据包。

建议使用：

```text
使用当前已选定的 vedic-core 或 vedic-core-pro，执行《Vedic盲问全量扫描与锁定协议 v1.3》。

盲问问题：
1. [问题一]
2. [问题二]

候选范围：[例如2016-01-01至2026-07-24]
指标定义：[例如“年度事业/经营收入，不等于资产增加或现金留存”]
是否强制单选：[是/否]
盲审等级：[UC隔离盲审／防泄漏盲测]

UC只作隔离，不得参与盘面结论。完整枚举范围内全部候选，
展示加权正反矩阵；找到强点后仍扫描到范围终点。
```

## 一、输入隔离

### 1. 两种盲审等级

#### A. UC隔离盲审（默认）

- 可以在已有UC、已有报告或已有传记信息的任务中执行。
- UC属于“可见但禁止作为推理证据”的隔离层。
- 如果正确答案已经出现，标记：
  `答案已知：本轮为回溯式全量盲审，不计为独立盲测命中。`
- 答案已知不构成停止条件。仍须完整扫描全部候选，并允许最终排序与已知答案不同。
- 不允许用UC决定先看哪一年、哪个信号更重要、何时停止或怎样打破平局。

#### B. 防泄漏盲测（仅在用户明确要求时）

- 必须新建任务，不继承含用户经历、正确答案或反馈的旧对话。
- 只使用净化数据包，不允许用“请忘记前文”冒充上下文隔离。
- 如果答案在锁定前泄漏，降级为“回溯式全量盲审”，不得继续声称独立盲测。

### 2. 盘面证据白名单

先继承当前已经选定的core报告谱系，不在盲问阶段重新选版。两种谱系共同允许
`structured_data.md` 中的纯盘面、Dasha与校验数据；其余白名单分别是：

标准版 `vedic-core`：

- `p1_overview.md`；
- `p2a_planets.md` 至 `p2d_planets.md`；
- `p3a_d9.md`、`p3b_divisional.md`；
- `p4a_houses.md`、`p4b_houses.md`；
- `appendix.md`。

Pro版 `vedic-core-pro`：

- `p0_identity.md`；
- `p2a_planets.md` 至 `p2d_planets.md`；
- `p3a_d9.md`、`p3b_divisional.md`、`p3c_yogas.md`；
- `p4a_houses.md`、`p4b_houses.md`；
- `p5_prediction.md`、`p5c_topics.md`；
- `appendix.md`。

不得跨谱系拼接白名单。若目录同时出现两套独占标记且当前选择不明确，先确认
哪一套报告是本轮权威来源，再开始扫描。

文件存在于任务中，不等于其中所有文字都自动获得证据资格。任何用户事实、
验前事反馈或事后解释都必须从推理层排除。

### 3. UC隔离规则

以下信息可以因正常core Q&A伦理要求而被读取，但不得作为盲审结论的证据：

- `user_context.md`；
- 当前聊天和先前聊天摘要中的用户传记、事件、答案与反馈；
- 标准版 `p5a_life.md`、`p5b_life.md`，以及Pro版 `p6a_life.md`、
  `p6b_life.md`、`p6c_blueprint.md` 中引用的已确认事实；
- `qa_*.md`、`archive_*.md`；
- `rectification_report.md`及事件校准材料；
- 已生成HTML/PDF报告和聊天截图。

执行要求：

- “允许读取”不等于“允许参与推导”。如果当前所选core引擎的Q&A要求读取UC，
  只用于伦理红线检查，不得用于选择盘面结论。
- 每个结论必须能够从上方盘面证据白名单独立复现。
- 不得从已知事实出发，再去寻找一个能解释它的盘面点。
- 不得因为某个候选与UC吻合，就提高权重、置信度或停止后续扫描。
- p系列文件若混有用户事实，只使用能够回溯到盘面数据的审计结论；
  无法分离时标记`UC隔离失败`，不得把该段当证据。
- 完成矩阵后执行反事实检查：如果用户报告的是相反结果，候选排序是否仍相同？
  若不同，重新计算受影响部分。

### 4. 防泄漏盲测的额外净化要求

用于盲问的 `structured_data.md` 必须删除或遮蔽：

- `用户信息`；
- 婚姻状态、职业、财务、家庭等现实事实；
- `信号修正日志`；
- `验前事结果`；
- `事件对照`；
- 用户原话、命中/未命中反馈；
- 任何能够直接泄露答案的日期。

如果p系列文件中出现经确认的用户经历，防泄漏盲测应排除该文件或先制作净化副本。
这项硬隔离只适用于B级防泄漏盲测，不是A级UC隔离盲审的启动门槛。

## 二、开始前必须公开的执行信息

在做任何判断前，先在聊天框写清：

1. 选用的skill：当前已锁定的 `vedic-core` 或 `vedic-core-pro`；
2. 当前子阶段：`Q&A／盲问锁定`；
3. 使用的工作时间与出生地点；
4. 用户授权的候选范围；
5. 当前全部候选；
6. 本轮必须展示的矩阵；
7. 锁定答案所需的完成条件；
8. 盘面证据白名单与UC隔离范围；
9. 盲审等级、UC是否可见、答案是否已经可见。

未完成这段声明，不得开始判断。

## 三、问题定义

先把问题改写成可比较的指标，并让定义固定下来。

例如“收入最高”必须区分：

- 营业收入；
- 净收入/利润；
- 现金最宽松；
- 资产增加最多；
- 资源调动规模最大。

如果用户没有细分，默认使用“事业或经营活动形成的年度收入/营收”，并明确它不等于资产增加或现金留存。

如果用户问“感情变动”，定义为：

- 重要关系开始；
- 结束；
- 复合；
- 身份改变；
- 相处规则或承诺被重定。

不得预设一定是结婚、离婚或分手。

若问题包含多项事件，先确定候选单位是独立事件还是可能共享同一Dasha交接簇。
不得默认“一项事件对应一个年份/AD/PD”，也不得默认同窗事件一定同源。

## 四、全候选扫描

### 1. 禁止提前收敛

- 先按问题定义确定真正的候选单位，并完整枚举所有会影响答案的候选。
- 年度排名题中，授权范围内每一个公历年都必须进入矩阵。
- 事件类型、离散选项或其他盲问中，枚举该问题全部决策相关候选，不得机械改写
  成逐年排名。
- 找到第一个强候选后仍必须扫描到候选范围终点。
- 禁止只检查当前最喜欢的候选。
- 禁止用已知事件反向决定何时停止。

### 2. 时间候选按实际换挡切片

当候选是公历年或其他时间区间，且MD/AD/PD换挡会改变当前问题的证据时，必须按实际
换挡日期切片。年度排名题中的每个公历年均按此规则检查。

例如一年中4月更换小运，必须分别分析：

- 1月1日至换挡日；
- 换挡日至12月31日。

不得因为时间候选跨两个小运就降低分析深度。若换挡与问题无关或不会改变排序，
可在矩阵中简要标明“不构成区分”，不必机械扩写。

时间精度硬约束：

- 年度或阶段问题至少读取MD×AD；
- 月份、季度内排序或任何窄于完整AD的问题必须读取calculator原生MD×AD×PD；
- PD缺失或连续性校验失败时，输出“分辨率不足”并降级到AD窗口；
- 禁止按365.25天、比例拆分或小运中点自行补PD。

### 2.1 PD渐进披露（“全候选”不等于“全量展开729行”）

- 先用calculator的`dasha_query.py --overview`读取非PD数据和全部MD/AD，
  用`--check`验证canonical PD=729且`[start,end)`连续，但不把整表送入模型上下文。
- 先完成授权范围内**全部候选**的MD/AD矩阵、领域轴与形态轴审计。
  这里的“完整扫描”要求候选无遗漏、方法等深，不要求提前展开与结论无关的PD。
- 在MD/AD矩阵完成后，先锁定所有因月/日级问题、实际输出窄于AD、年度排序仍有决策相关细分需求，
  或handoff cluster而必须读PD的**全部合格候选**。
- 对该合格集合用`dasha_query.py --month/--date/--start --end --context 1`统一下钻；
  所有候选使用同一精度、相同相邻上下文和相同接力审计。
- 禁止只给当前领先/最喜欢的候选读PD；禁止边读PD边淘汰对手；
  禁止通读729行后反向挑一段最像已知答案的窗口。
- 若MD/AD已能结算问题且用户不要更细分辨率，停在AD。“更完整”不得被误解为必须读PD。

### 3. 换挡接力检查

对包含相关MD/AD换挡、且接力判断可能改变候选排序的时间候选，检查：

1. 前后两颗AD/PD主星是否指向同一事件链的不同环节？
2. 前一颗星是否负责启动、变现或拆旧？
3. 后一颗星是否负责扩大、维持、成交或结算？
4. 主题是中断，还是形成接力？

这些是判断提示，不是要求每次生成四段固定答案。只记录会影响证据或排序的结果。
禁止默认“小运换挡=主题混乱”，也禁止为了制造接力而强行把无关信号串成故事。

若边界一侧为Rahu/Ketu，优先按所选core已定义的节点结果引擎；若该谱系未另设名称，
仍至少追踪节点落宫/轴线、D1定位星、相关分盘定位星及相邻Dasha。节点与定位星相邻接棒时，自动建立
`handoff cluster`候选，但仍须用反证判断它是同一事件链还是换题。

### 4. 事件簇与多事件映射

- 候选可以是单一时段，也可以是由相邻AD/PD构成的Dasha交接事件簇；候选单位由
  实际边界与结构连接决定，不预设固定宽度。
- 同一枢纽星若独立连接多个问题领域，允许同一簇承载多项事件；逐项保留领域证据、
  形态证据与反证。
- 禁止为了让列表“整齐”，把结婚、晋升、丧失、搬迁等强制一对一分配给不同小运；
  也禁止仅因事件同窗就认定同源。
- “发现事件类型”和“把已知事件标签映射到时间”必须分开结算；答案已知时，后者只能
  标记为回溯映射，不能伪装成前者的盲猜命中。

### 5. 每个候选的统一审计维度

所有候选使用同一套适用的审计维度，保证比较口径一致。某一维度与当前问题无关、
对应分盘未启用或数据确实不可用时，对全部候选采用相同处理：简要说明原因后省略
或标记不可用，不得只对不喜欢的候选省略。表格可以合并相邻信息，但不能隐藏会
改变排序的依据：

| 审计维度 | 适用时必查内容 |
|---|---|
| MD背景 | 大运星D1角色、落宫、管宫、硬约束判定 |
| AD触发 | 小运星D1角色、落宫、管宫、候选内覆盖时段 |
| PD触发 | 月级/窄于AD/决策相关接力问题必查：用局部查询读三级运主星、精确`[start,end)`边界、与AD/相邻PD接力 |
| D1主题 | 问题对应宫位、宫主、Karaka、结构信号 |
| 相关分盘 | 财富/事业查D10；感情查D9；家宅查D4；创造/影响查D5 |
| Chara Dasha | 当年星座大运从Lagna落第几宫，是否同题 |
| 支持 | 标注★★★/★★☆/★☆☆ |
| 制约 | 标注★★★/★★☆/★☆☆ |
| 领域轴 | 宫主/Karaka/节点定位星/分盘回答“什么领域被点名” |
| 形态轴 | 尊贵、燃烧、Maraka适用语境、8/12宫、相关分盘承载回答事件形态 |
| 时间轴 | MD背景、AD阶段、PD月级候选、Chara/可复核过运确认 |
| 事件阶段 | 启动、正式化、结果、后处理、重建或换题 |
| 事件性质 | 收入、资产、周转、客户、关系、成本等，不得混写 |
| 年度结算 | 首选/强候选/次选/低可能，并解释原因 |

## 五、加权规则

严格沿用 `qa_rules.md` 的三轴结算：

- 领域轴：Karaka/D1结构/直接Dasha激活定领域，宫主路径/Yoga/相关分盘确认；
- 形态轴：尊贵、燃烧、Maraka适用语境、8/12宫、D9/D10承载与房东按形态直接性称重；
- 时间轴：MD定背景、AD定阶段、PD定月级候选，Chara/过运只作可复核确认。

每个轴内部称重量，禁止数条数；轴与轴之间不得投票。

领域轴的低权重信号不得否定高权重方向；但形态直接信号不得因为在领域轴权重低
而被降成“只是执行困难”。领域激活、事件形态与兑现时间必须分别锁定。

## 六、全矩阵完成后的头对头比较

只有所有候选都扫描完，才允许进入排序。

排序步骤：

1. 识别所有仍有实质竞争力的单段或事件簇候选，不预设人数上限，并保留并列；
2. 分别列出高权重支持；
3. 分别列出最高权重制约；
4. 比较事件性质是否真正吻合问题指标；
5. 比较AD/PD在候选区间的覆盖长度及交接阶段；
6. 检查是否只有宽窗口、没有年度区分信号；
7. 给出领先候选的排序、并列或区间，并说明其真实分辨率。

禁止用“小运中点”“感觉最完整”“第一眼最像”等skill未定义的规则打破平局。

## 七、时间分辨率与置信度

### 唯一年份准入

只有出现至少一个**独立年度区分信号**时，才能把某一年单独排在相邻年份前面，例如：

- 当年发生MD/AD切换且前后形成独特接力；
- 当年/月发生PD切换且前后形成与相邻候选不同的独特接力；
- 直接财富/关系宫主在当年大部分时间被激活；
- 相关分盘出现与相邻年份不同的明确触发；
- 第二时间系统在当年提供同题确认。

### 无法区分时

- 输出并列候选或窄区间；
- 如果用户强制单选，必须写：
  `低置信强制单选，不代表盘面已具备单年分辨率。`
- 不得把区间的高置信度继承给单年。
- 不得发明新规则打破平局。

## 八、答案锁定

如果答案尚未出现，反馈前必须先写入：

`qa_盲问锁定_主题.md`

文件必须包含：

- 问题与指标定义；
- 数据白名单；
- 排除文件；
- 完整候选矩阵；
- 所有实质竞争候选的头对头比较；
- 最终单选或区间；
- 置信度；
- 明确声明“反馈前锁定”。

如果答案已经可见，仍须先完成全矩阵，再写入：

`qa_盲问回溯重判_主题.md`

文件须明确声明：

`答案在分析前已经可见；本文件记录UC隔离后的全量重判，不是反馈前预提交。`

写完后运行：

```bash
shasum -a 256 [本轮实际输出文件]
```

把哈希和锁定时间写在聊天框中。锁定后不得覆盖该文件。回溯重判的哈希只能证明
锁定后的内容未被改写，不能证明答案在分析前未知。

## 九、接收反馈

答案尚未出现时，锁定后向用户询问结果。可以提供以下快捷分类，但不得限制用户
只能三选一；同时允许自由说明、事实纠正和补充实际答案：

- 命中；
- 部分命中；
- 未命中。

答案已经可见时，不再重复索取反馈；先锁定全量重判，再把与已知答案的比较写入
单独的 `qa_盲问复盘_主题.md`，不得回头修改候选排序。

收到反馈后：

- 不修改锁定文件；
- 单独创建 `qa_盲问复盘_主题.md`；
- 正确项解释为什么命中；
- 错误项解释漏扫、权重或时间分辨率问题；
- 不把事后可解释写成事前已预测；
- 不回填答案后重新声称“这本来就是第一候选”。

## 十、停止与降级条件

出现以下任一情况，停止本轮判断：

- 候选范围不明确；
- 指标定义无法确定；
- 出生时间或相关分盘不可用，而问题又依赖该分盘；
- 用户要求的单年精度超过现有数据分辨率，却不允许低置信标注。

出现以下情况不停止，但必须降级或标记：

- 防泄漏盲测中答案提前出现 → 降级为回溯式UC隔离盲审；
- UC存在或已被读取 → 保持UC隔离盲审，只要结论仍能由盘面证据独立复现；
- p系列文件混有用户事实 → 排除事实段并回溯纯盘面依据；
- 事实与盘面结论无法分离 → 标记`UC隔离失败`，该结论不得交付为盲审结果。

## 最短触发词

默认的UC隔离盲审在当前任务或新任务都可使用：

```text
按全局文件《Vedic盲问全量扫描与锁定协议 v1.3》执行。
盲审等级：UC隔离盲审。
问题：[填写]
范围：[填写]
指标：[填写]
强制单选：[是/否]
UC可以存在，但不得参与盘面结论、候选排序、权重或停止点。
完整扫描全部候选，找到强点后继续扫到终点，再锁定结果。
```

只有需要证明答案事前未知时，才把“盲审等级”改为“防泄漏盲测”，并在新任务中
使用净化数据包。
